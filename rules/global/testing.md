# Testing Rules

## 测试原则

测试目标不是追求测试数量，而是验证：

1. 正常行为
2. 边界行为
3. 异常行为
4. 回归风险

## 新功能

新功能至少考虑：

- Happy Path
- Boundary Case
- Error Case

例如：

- 输入正常值
- 输入空值
- 输入非法值
- 输入最大值
- 输入不存在的数据
- 依赖服务失败

## Bug 修复

Bug 修复必须优先考虑增加能够复现该 Bug 的测试。

推荐流程：

```text
复现 Bug
↓
编写失败测试
↓
修复代码
↓
测试通过
↓
运行相关回归测试
```

## 修改已有逻辑

如果修改已有业务逻辑：

1. 找到已有测试
2. 运行已有测试
3. 修改代码
4. 增加必要测试
5. 运行回归测试

## 测试失败

测试失败时不要直接修改测试让它通过。

首先判断：

```text
代码错误？
测试错误？
环境问题？
依赖问题？
测试数据问题？
```

只有确认测试本身错误时才修改测试。

## 验证优先级

优先执行最接近修改范围的测试：

```text
单元测试
↓
模块测试
↓
集成测试
↓
完整测试
↓
构建
```

## 完成标准

最终必须明确报告：

```text
TypeCheck: PASS/FAIL/N/A
Lint: PASS/FAIL/N/A
Test: PASS/FAIL/N/A
Build: PASS/FAIL/N/A
```

不能使用：

```text
应该没问题
看起来没问题
应该可以
```

代替实际验证。
