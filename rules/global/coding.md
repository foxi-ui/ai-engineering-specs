# Coding Rules

## 目标

编写可维护、可测试、可理解的生产级代码。

## 核心原则

### 1. 优先理解现有代码

修改代码之前：

1. 阅读相关文件
2. 查找调用方
3. 查找被调用方
4. 理解数据流
5. 理解现有架构和项目约定
6. 优先复用已有能力

不要在没有理解现有实现的情况下直接重写。

### 2. 最小修改原则

解决问题时优先：

- 修改最少的文件
- 修改最少的代码
- 保持现有 API
- 保持现有行为
- 不做无关重构

如果发现确实需要扩大修改范围，先说明原因。

### 3. 不重复造轮子

实现功能之前检查：

- 项目已有 utils
- 项目已有 hooks
- 项目已有 components
- 项目已有 services
- 项目已有公共方法
- 已安装依赖
- 已存在类似实现

优先复用。

### 4. 类型优先

TypeScript 项目：

- 优先使用明确类型
- 避免 `any`
- 避免无意义的类型断言
- 公共 API 必须定义类型
- 函数参数和返回值应尽可能明确

Java 项目：

- 明确 DTO / VO / Entity 边界
- 避免使用 `Map<String, Object>` 代替明确模型
- 公共方法明确参数和返回值

### 5. 错误处理

不要吞掉异常：

```ts
try {
  doSomething()
} catch (error) {
}
```

也不要只使用日志代替错误处理：

```ts
try {
  doSomething()
} catch (error) {
  console.log(error)
}
```

必须根据业务决定：

- 是否重新抛出
- 是否转换错误
- 是否记录日志
- 是否返回默认值
- 是否通知用户

### 6. 不修改无关代码

禁止为了“顺便优化”修改：

- 无关组件
- 无关依赖
- 无关格式
- 无关命名
- 无关架构

除非该修改是当前任务的必要条件。

### 7. 注释原则

优先解释：

> 为什么这么做

而不是：

> 这里调用 xxx 方法

复杂逻辑、兼容性处理、业务规则必须解释原因。

### 8. 兼容性

修改代码前确认：

- Node 版本
- 浏览器兼容范围
- TypeScript 版本
- Framework 版本
- 构建工具版本
- 依赖版本

不要默认使用当前最新语法或 API。

### 9. 完成标准

代码修改完成不代表任务完成。

任务只有在适用的：

- 类型检查
- Lint
- 测试
- 构建
- Review

完成后才能宣布完成。
